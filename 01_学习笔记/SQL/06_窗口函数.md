## 1. 窗口函数与 GROUP BY 的区别

`GROUP BY` 把多行合并成分组结果。例如按客户汇总金额，每个客户只剩一行。窗口函数则在保留当前结果每一行的同时，查看一组相关行，计算总额、序号或排名。

“窗口”就是当前计算能看到的行集合。`OVER (...)` 定义这个集合：

- `OVER ()`：把当前查询结果的全部行作为一组。
- `PARTITION BY 列`：按该列分区，各区独立计算，区内明细行仍然保留。
- `ORDER BY 列`：规定区内计算顺序，不等同于最终输出排序。

先对每笔已支付订单显示“本笔金额”和“全部已支付金额”：

```sql
WITH paid_detail AS (
    SELECT o.order_id, o.quantity * p.unit_price AS amount
    FROM orders AS o
    INNER JOIN products AS p ON o.product_id = p.product_id
    WHERE o.status = 'paid'
)
SELECT order_id, amount,
       SUM(amount) OVER () AS all_paid_amount
FROM paid_detail
ORDER BY order_id;
```

结果仍是 7 行，`amount` 依次为 6、5、9、8、5、3、4，新增列 `all_paid_amount` 每行都是 `40.00`。窗口计算没有把 7 行合并成 1 行。

CTE 先完成金额计算，主查询对它使用窗口函数。这样每层负责一件事，便于检查数据范围。

## 2. ROW_NUMBER：给每个客户的订单编号

`ROW_NUMBER()` 从 1 开始为每一行分配连续序号。`PARTITION BY customer_id` 表示每个客户重新从 1 开始；降序排列订单日期和编号，就把最近的订单放在前面。

```sql
SELECT customer_id, order_id, order_date,
       ROW_NUMBER() OVER (
           PARTITION BY customer_id
           ORDER BY order_date DESC, order_id DESC
       ) AS rn
FROM orders
WHERE status = 'paid'
  AND customer_id IS NOT NULL
ORDER BY customer_id, rn;
```

| customer_id | order_id | order_date | rn |
| --- | --- | --- | --- |
| 1 | 1008 | 2026-10-04 | 1 |
| 1 | 1002 | 2026-10-01 | 2 |
| 1 | 1001 | 2026-10-01 | 3 |
| 2 | 1005 | 2026-10-03 | 1 |
| 2 | 1003 | 2026-10-02 | 2 |
| 4 | 1006 | 2026-10-03 | 1 |

同一天可以有多笔订单，因此用唯一订单编号打破并列，结果可重复获得。这里“最近”明确按日期，再按编号排序，并不声称编号本身记录了精确下单时间。

找每个客户最近一笔，需再套一层 CTE：

```sql
WITH ranked_orders AS (
    SELECT customer_id, order_id, order_date,
           ROW_NUMBER() OVER (
               PARTITION BY customer_id
               ORDER BY order_date DESC, order_id DESC
           ) AS rn
    FROM orders
    WHERE status = 'paid'
      AND customer_id IS NOT NULL
)
SELECT customer_id, order_id, order_date
FROM ranked_orders
WHERE rn = 1
ORDER BY customer_id;
```

结果为客户 1→1008、客户 2→1005、客户 4→1006。不能在同一层的 `WHERE` 里使用 `rn`：这一层筛选发生在窗口结果生成之前。先计算再到外层筛选。

此查询只输出有支付订单的已登记客户。若保留匿名订单，所有 `customer_id IS NULL` 的行会进入同一个空值分区，不能把它解释为同一个真实客户。

## 3. RANK 与 DENSE_RANK：有并列时如何编号

排名之前通常先汇总。以下先统计每种商品的已支付件数，包含零销量商品，再排名：

```sql
WITH product_totals AS (
    SELECT p.product_id, p.product_name,
           COALESCE(SUM(o.quantity), 0) AS total_quantity
    FROM products AS p
    LEFT JOIN orders AS o
        ON p.product_id = o.product_id
       AND o.status = 'paid'
    GROUP BY p.product_id, p.product_name
)
SELECT product_id, product_name, total_quantity,
       RANK() OVER (ORDER BY total_quantity DESC) AS rank_no,
       DENSE_RANK() OVER (ORDER BY total_quantity DESC) AS dense_rank_no
FROM product_totals
ORDER BY total_quantity DESC, product_id;
```

| product_id | product_name | total_quantity | rank_no | dense_rank_no |
| --- | --- | --- | --- | --- |
| 1 | pen | 6 | 1 | 1 |
| 3 | eraser | 6 | 1 | 1 |
| 2 | notebook | 2 | 3 | 2 |
| 4 | mug | 0 | 4 | 3 |

`RANK()` 并列同名次，后面的名次跳号；两个第一名之后是第三名。`DENSE_RANK()` 也并列同名次，但名次连续，两个第一名之后是第二名。

`ROW_NUMBER()` 总是每行一个不同的序号。要稳定区分两件销量相同的商品，可使用 `ORDER BY total_quantity DESC, product_id`。

但上例的 `RANK` 和 `DENSE_RANK` 窗口中不要添加 `product_id`：排名按窗口中的全部排序列判断并列，加入唯一编号就会拆散同销量的并列。最终输出的 `ORDER BY` 可以添加编号，它只是让同名次商品按编号稳定显示。

## 4. 累计金额：明确累计到当前行

累计值按顺序逐行相加。例如 6 → 11 → 20，不是每行都显示最终总额 40。

```sql
WITH paid_detail AS (
    SELECT o.order_id, o.order_date,
           o.quantity * p.unit_price AS amount
    FROM orders AS o
    INNER JOIN products AS p ON o.product_id = p.product_id
    WHERE o.status = 'paid'
)
SELECT order_id, order_date, amount,
       SUM(amount) OVER (
           ORDER BY order_date, order_id
           ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
       ) AS running_amount
FROM paid_detail
ORDER BY order_date, order_id;
```

| order_id | order_date | amount | running_amount |
| --- | --- | --- | --- |
| 1001 | 2026-10-01 | 6.00 | 6.00 |
| 1002 | 2026-10-01 | 5.00 | 11.00 |
| 1003 | 2026-10-02 | 9.00 | 20.00 |
| 1005 | 2026-10-03 | 8.00 | 28.00 |
| 1006 | 2026-10-03 | 5.00 | 33.00 |
| 1007 | 2026-10-04 | 3.00 | 36.00 |
| 1008 | 2026-10-04 | 4.00 | 40.00 |

`ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` 叫作窗口框架，定义本行的计算范围：

- `ROWS` 按排序后的行计范围。
- `UNBOUNDED PRECEDING` 表示从分区第一行开始。
- `CURRENT ROW` 表示到当前行结束。

本例没有 `PARTITION BY`，所以全部已支付订单在一个分区内。若添加 `PARTITION BY customer_id`，就变成各客户分别累计，需同时决定如何处理匿名客户。

写累计值时显式写出 `ROWS ...` 并补齐排序列。仅按日期排序且省略框架时，同日的多行可能共享累计结果，与“逐笔累计”不同。

## 常见错误和边界

- 把窗口函数当成分组，误以为客户会只剩一行；检查结果行数是否与输入明细相同。
- 在本层 `WHERE` 使用窗口函数或窗口别名；改成 CTE 中计算、外层筛选。
- 只在窗口里排序，忘记最终 `ORDER BY`；窗口计算顺序不保证输出顺序。
- 排名时为避免显示顺序不确定，把唯一编号放进 `DENSE_RANK` 的排序，结果破坏并列。显示排序和排名标准要分别决定。
- 先在外层过滤掉部分订单再累计，会改变累计范围；问清是在“全部订单中排名后选出”，还是“先筛选再排名”。
