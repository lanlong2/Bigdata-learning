# 案例01｜状态变化与事务

这是J03—J04阶段的概念讲解，不是用户已完成代码。先学习数据库更新、事务和Java方法调用；版本号条件更新在读完本页后再按教材练习。

## 业务问题

工单42目前为“处理中”，处理人为用户7。处理人提交解决结果后，系统需要把工单改为“已解决”，并写一条“用户7提交解决结果”的操作历史。

这不是两个互不相关的功能：状态变化应该能追溯到发生的操作，失败时不应留下“状态改了、历史没有”的半成品。

## 事务让哪些步骤一起成功

事务是一组数据库操作共同成功或共同撤销的范围。此处可以把以下步骤放在同一事务中：

1. 检查工单存在、当前操作人为处理人、当前状态允许解决、解决说明非空。
2. 按当前状态和版本条件更新工单。
3. 确认成功更新一行后，写入操作历史。
4. 都成功才提交；任一步失败，撤销本次事务中的修改。

若历史写入失败，应观察工单仍为原状态、历史没有新增，而不是只看接口返回错误。框架中的事务声明还涉及调用方式与异常处理，学习J04后需要核对实际是否生效，不能看到注解就认定测试通过。

## 事务之外还要看并发

并发是两个请求重叠执行。假设请求A和B都读到版本3、状态“处理中”；A先解决，B随后把同一工单也标成解决并写第二条历史。如果只是先查询、再无条件更新，可能发生这种重复。

版本号是记录上一个随修改递增的数字。更新时要求记录仍然处于读到的版本，相当于说：“只有它还没有被别人改过，才应用我的这次修改。”

| 时刻 | 请求A | 请求B |
|---|---|---|
| 1 | 读到版本3、处理中 | 读到版本3、处理中 |
| 2 | 按版本3与状态条件更新，成功一行，变成版本4 | 尚未更新 |
| 3 | 在同一事务写历史并提交 | 按版本3条件更新，成功行数为0 |
| 4 | 返回成功 | 返回状态已变化的冲突提示，不写解决历史 |

实现时应同时约束处理人、允许状态与版本，并核对更新行数。业务身份校验仍然需要，版本号不能替代权限。

## 如何核对而不只看正常流程

| 场景 | 预期 |
|---|---|
| 处理人正常解决 | 状态、版本与历史一起更新 |
| 非处理人操作 | 工单不变，历史不增加 |
| 空解决说明 | 返回输入错误，不写入 |
| 历史写入失败 | 状态更新撤销，没有部分成功 |
| 两个请求使用同一旧版本 | 至多一个按该旧版本成功，另一个获得冲突 |
| 已解决工单再次解决 | 按业务约定拒绝或返回已完成结果，不重复增加解决历史 |

测试并发时需要安排两个请求读取同一版本，或直接明确提供相同旧版本；只手动快速点两次而没有控制条件，不能证明已经覆盖冲突情形。若故意制造失败，标为故障演练，不写成真实线上事故。

## 就地练习

先用自己的话回答：如果工单更新放在事务外而历史写入放在事务内，历史失败会怎样？如果只校验版本、不校验处理人，会有什么问题？如果更新行数为0后仍然写历史，会留下什么不一致？

学完J04后，用当前已学框架实现最小版本，再核对三种场景：正常解决、历史失败回滚、旧版本冲突。完成检查：能讲清事务与并发条件分别解决什么问题，并从实际数据核对状态与历史是否一致。
