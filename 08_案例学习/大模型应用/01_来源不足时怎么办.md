# 案例01｜来源不足时怎么办

这是A04阶段的概念示例，资料为本案例虚构，不代表真实企业制度；不是用户项目的已完成实现。先理解RAG、资料段落、模型API和HTTP接口，再阅读。

## 问题与资料

RAG会先找与问题相关的资料，再把相关段落交给模型。相似的词可能出现在很多不同问题里，“找到了相关内容”并不等于“已经找到答案”。

本例资料库只有两个有效段落：

| 来源标识 | 标题 | 原文 |
|---|---|---|
| guide-v1-p1 | 设备报修说明 | 设备故障请在工单中填写设备编号、现象与联系方式。 |
| guide-v1-p2 | 处理时间说明 | 工作日收到工单后，支持人员会在一个工作日内首次响应。 |

问题一：“报修要填什么？”问题二：“设备坏了多久一定修好？”

## 先判断能不能回答

问题一能直接由p1回答。问题二虽然与p2有关，但“首次响应”是第一次回复或联系，“修好”是问题解决；原文没有承诺解决时限。

| 问题 | 检索到的相关段落 | 正确处理 |
|---|---|---|
| 报修要填什么 | p1 | 回答设备编号、现象和联系方式，引用p1 |
| 多久一定修好 | p2 | 说明资料只规定首次响应时间，没有修复完成时限 |
| 非工作日多久响应 | p2 | 说明现有资料没有非工作日规则，不把工作日规则直接外推 |

因此，问题二若回答“一天内一定修好”，语言再流畅也属于没有依据的结论。

## 回答与来源怎样一起核对

可回答问题的概念性响应如下；它是接口数据说明，不是用户已经实现的代码：

```json
{
  "answer": "请填写设备编号、故障现象和联系方式。",
  "sources": [{"id": "guide-v1-p1", "title": "设备报修说明"}],
  "answerable": true
}
```

无依据问题可以返回`answerable: false`，并说明“资料没有给出修复完成时限；仅提到工作日内的首次响应时间”。可以附p2用于解释已知范围，不能把它标为修好时间的证据。

每次至少核对三点：来源标识是否真实存在，引用原文是否支持关键事实，回答是否把资料中没有的条件或数字补了出来。资料包含互相矛盾的版本时，先说明冲突或按明确版本规则选择，不能随机选一句当最终制度。

## 从失败找到改进方向

| 现象 | 更可能检查的环节 | 合理的下一步 |
|---|---|---|
| p1根本没有被找出 | 文本导入、切分、检索 | 核对段落是否入库、实际检索结果及不同问法 |
| 找到了p2却回答一天修好 | 上下文理解、输出限制 | 明确“首次响应”与“解决”，加入无依据问题检查 |
| 回答正确但引用不存在 | 引用生成与响应校验 | 只允许引用实际检索来源，响应后验证标识 |
| 同一问题偶尔回答偶尔拒答 | 模型配置、检索波动 | 固定版本并多次记录，明确随机性和已知限制 |

先保留基线结果，只改一个主要因素再比较；不要同时换模型、检索方案和问题集，导致无法说明改进来自哪里。

## 就地练习

不写代码，先对三条新问题判断“能回答／应说明缺失”，并指出依据：“需要写手机号吗？”“节假日会有人修吗？”“工作日一定当天有回复吗？”注意原文只说“联系方式”，没有限制为手机号；“一个工作日内”也不等于“当天”。

再写一个能防止外推的判定规则，并为每题保存自己的理由。完成检查：能解释相关性与证据的区别、能识别条件被改变、能给无依据问题清楚的答复。阅读和练习完成按用户后续说明记录。
