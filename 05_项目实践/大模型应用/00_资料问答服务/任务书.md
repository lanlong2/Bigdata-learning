# 资料问答服务｜任务书

这是A05的学习任务，尚未记录用户开始或完成。项目预算45小时；前置为A00 SQL、A01 Python工程、A02 HTTP与FastAPI、A03模型API、A04 RAG与评测。超出前置的功能先列为扩展，不能要求边做项目边补一整套训练课程。

## 要解决的问题与范围

选一组有权使用的资料，例如虚构企业操作说明或公开使用指南。用户通过HTTP接口提问，系统从资料中找到依据，输出回答、来源和必要的限制说明。

RAG即“先检索资料，再将相关内容交给模型生成回答”。检索不是保证事实正确的凭证，模型仍可能漏读或编造，因此必须核对来源和拒答情况。

首版限定单一资料库和少量纯文本或Markdown文件；不做网页采集平台、复杂PDF解析、训练、深入微调、复杂多Agent、完整前端和高并发平台。模型使用可替换的API配置，不把特定硬件或本地大模型部署设为完成前置。

## 核心功能

| 功能 | 需要实现的行为 | 至少核对的场景 |
|---|---|---|
| 导入与更新 | 给资料分配稳定标识，保存标题、版本和段落来源；重复导入行为明确 | 空文件、重复资料、更新后旧段落是否残留 |
| 资料检索 | 将资料拆成便于检索的段落，返回相关内容和标识 | 相同意思的不同问法、无关问题、相似标题 |
| 回答与引用 | 输出回答和可定位到原文的引用；引用只来自本次检索的真实资料 | 来源标识有效，引用段落确实支持回答中的关键说法 |
| 无依据处理 | 资料不足或冲突时拒绝给确定结论，说明缺少什么 | 资料外问题、关键信息缺失、版本冲突 |
| HTTP接口 | 明确请求、响应与错误格式；限制输入长度和单次处理范围 | 空问题、超长输入、错误字段、服务不可用 |
| 状态与日志 | 可查询服务状态；记录请求标识、耗时和失败环节 | 检索失败、模型超时、数据库错误可分别定位 |
| 成本与配置 | 密钥通过环境配置读取；限制最大输入、输出和调用次数 | 缺少密钥时给清晰错误，重试有限制，日志不泄露密钥 |

项目若使用MySQL，使用独立数据库`llm_qa_app`，在初始化脚本中明确选库，不清理或混用`sql_learning`。保存资料元信息、导入记录或问答记录即可，不为增加组件而重复保存全部数据。向量检索方案在A04选定后写进技术说明。

原文中的“忽略规则”等指令作为资料内容处理，不能取得系统操作权限。工具调用若使用，仅允许只读、范围受限的操作；该项目不必引入工具调用才能完成。

## 怎样建立可说明的评测

评测集是固定的问题及预期判定依据，用来比较修改前后的效果。先准备约30个问题，覆盖直接问答、换一种问法、需要两段资料、资料外问题和信息冲突；给出每题的参考来源与“可回答／应拒答”分类。

可把10题用于开发调试，另20题用于阶段检查。看过阶段检查结果并用其调参后，应说明它已经参与开发；后续补充新问题，不能继续宣称完全未见。数量可按资料规模调整，须保持各类场景覆盖。

至少比较“简单基线”与“改进版”：基线是最初的切分和检索方案；改进只变动一个主要因素，例如段落长度或检索条数。记录资料版本、模型配置、问题、检索段落、回答、引用、耗时和判定理由。API费用有实际数据就记录，没有就只记录调用量等可观测值，不编造金额。

按类别报告：关键事实是否有资料支持、引用是否有效、应拒答时是否拒答，以及耗时和调用量。人工判断要写出规则；自动评分只能作为辅助，不能让同一模型的一句“正确”成为全部证据。保留失败案例及修复前后对比，不预填漂亮数字。

## 建议执行分配

| 工作 | 时间 |
|---|---:|
| 确定资料、场景、接口与评测规则 | 5小时 |
| 完成接口、配置与资料导入流程 | 8小时 |
| 完成检索、回答、引用和拒答 | 12小时 |
| 运行评测并作一次有依据的改进 | 8小时 |
| 测试、异常排查与可复现部署 | 8小时 |
| 整理技术说明、局限与演示流程 | 4小时 |
| 合计 | 45小时 |

这是控制范围的安排，不是做满小时自动达标。遇到偏差先削减扩展功能；必要的额外补弱与返修从共用75小时预算安排，不挤占Java主学习预算。

## 最终交付与质量目标

- 用户编写的服务代码、依赖清单、配置示例；示例中只有配置名和占位值，没有真实密钥。
- 有来源与字段说明的演示资料、初始化方法、清理范围和数据版本。
- 能照着从空环境运行的README，包括启动、正常请求、失败请求、测试和已知限制。
- 自动化测试至少覆盖资料更新、引用标识、输入校验、无依据分支和上游服务失败；外部模型可用模拟响应测试，实际调用效果另行评测。
- 评测问题、判定规则、实际结果、失败分析与一次改进对比。
- 能独立修改一条需求，例如新增资料版本或调整引用格式，并解释相关代码及影响。

本项目不以添加很多框架为优秀标准。若重要场景仍失败，应修复或明确缩小可用范围，不能只展示最好的一条回答。基础阶段不使用AI代写；复杂项目阶段可以部分使用AI，前提是能够解释、修改、测试和维护对应代码。

这些是学习目标和检查建议。用户明确说明完成、订正、掌握或实际用时时，直接记录对应事实，不要求先提交证据；后续技术分析与完成记录分别保存。
