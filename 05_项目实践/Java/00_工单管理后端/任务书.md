# 工单管理后端｜任务书

这是J06的学习任务，尚未记录用户开始或完成。项目预算100小时，前置为J00—J05；日常练习、技术解释、测试和排错都计入学习时间。

## 业务范围

工单是用户提交的一条需要处理的问题记录，包含标题、描述、提交人、处理人、优先级与状态。系统用于演示完整处理流程；使用虚构用户和演示数据，不依赖真实企业系统。

首版做单体后端，使用Java、Spring Boot、MyBatis、MySQL 8.4 LTS，以及已学的测试工具。MySQL业务库使用`ticket_backend`，初始化脚本明确作用范围；课程库`sql_learning`及原项目资料保留。

暂不引入微服务、分布式事务、复杂消息系统、完整前端和多租户平台。Redis按明确需求选择使用，不为增加组件数量而缓存所有查询；AI接入属于核心完成后的选项。

## 角色与业务规则

| 角色 | 允许的主要操作 | 必须阻止的操作 |
|---|---|---|
| 提交者 | 创建工单、查看自己的工单、补充评论、确认关闭或重新打开 | 查看他人工单、分派处理人、冒充其他用户 |
| 处理人员 | 查看分配给自己的工单、开始处理、提交解决结果、评论 | 修改未分配给自己的工单、跳过业务状态限制 |
| 管理员 | 查看全部工单、分派与改派、查看操作记录 | 绕过输入校验、伪造已经发生的历史操作 |

身份信息来自登录后的可信身份上下文，不能把请求体中的`userId`直接作为操作人。登录凭证不能明文存储；复用框架提供的密码散列能力，不自创加密算法。认证方案在J04学习后确定并说明退出或过期行为。

状态采用以下明确规则，后续可以有依据地调整，但不能任意设置状态：

| 当前状态 | 操作 | 下一状态 | 条件 |
|---|---|---|---|
| 新建 | 分派 | 待处理 | 管理员选择有效处理人员 |
| 待处理 | 开始处理 | 处理中 | 由当前处理人操作 |
| 处理中 | 提交解决结果 | 已解决 | 解决说明非空 |
| 已解决 | 确认关闭 | 已关闭 | 由提交者确认 |
| 已解决 | 重新打开 | 待处理 | 提交者给出原因，保留原处理人 |

改派只在待处理或处理中允许；改派后进入待处理并保留历史。已关闭首版不再修改状态。非法操作不得产生部分更新。

## 数据与接口

自行设计用户、工单、评论和操作历史等必要表，说明主键、关联关系、必填字段、唯一性和索引选择。时间字段使用统一约定并在说明中写清；评论与状态历史不靠覆盖工单描述保存。

接口至少覆盖登录、创建、详情、列表、分派、开始处理、解决、关闭、重新打开与评论。为请求和响应写出字段、校验规则、成功示例与错误示例。错误格式统一，区分未登录、无权限、资源不存在、输入错误、状态冲突与内部失败。

列表支持状态、处理人或时间范围等必要筛选，稳定排序与分页。相同时间用唯一标识打破排序并列。限制页大小，明确空结果、非法页码和时间边界的行为。权限过滤必须进入查询条件，不能查询全部记录后再在内存中遮挡数据。

## 事务和并发场景

事务表示一组数据库修改作为一个整体成功或失败。例如状态变化及对应操作历史应一起保存：历史写入失败，状态变化也应回滚。用测试或可复现步骤验证，不能只写一个注解便认定正确。

并发是两个请求在时间上重叠处理同一条记录。至少解决“两个处理请求都读取旧状态，然后先后覆盖”的问题。可选择版本号条件更新等已学方案，检查受影响行数并返回状态冲突；不要只是读到状态后无条件更新。

在技术说明中回答：

1. 哪些操作必须原子完成，事务边界放在哪里，失败怎样回滚？
2. 两个用户同时修改同一工单时，怎样避免覆盖，调用方会得到什么结果？
3. 重复发送关闭或解决请求时，最终状态与历史条数怎样约定？
4. 权限校验与数据更新之间的业务条件是否仍可能变化，怎样在更新时重新约束？

## 有依据的查询优化

先建立正确查询，再用可复现的演示数据观察执行计划和耗时。选择至少一个真实查询场景，例如“查询某处理人的待处理工单并按时间分页”。说明筛选、排序、数据量、索引前后执行计划，以及是否存在写入或存储代价。

优化可以是索引、查询改写或避免多余查询。记录环境、重复测量方法与数据规模；结果没有显著加速时，如实分析，不编造高并发或百倍提升。若用Redis，应额外说明缓存键、有效期、数据更新和缓存不可用时的行为；没有收益依据时保持直接数据库查询也可。

## 测试、排错与复现

- 关键流程：创建→分派→处理→解决→关闭，以及重新打开、改派。
- 权限：匿名访问、越权查询、伪造操作人、非处理人更新。
- 数据边界：空标题、超长描述、无效关联用户、空列表、分页排序并列。
- 一致性：状态与历史回滚、并发冲突、重复请求。
- 故障：数据库不可用、配置缺失、未预期异常；响应给出适当提示，日志能定位到请求和环节，避免输出密码或访问凭证。

业务规则用单元测试验证，数据库、事务与接口行为用集成测试或明确的复现步骤核对；测试准备数据相互隔离。保留至少几个真实排错过程：现象、缩小范围、原因、修复与回归检查。若尚未发生某种错误，不伪造排障经历，可以明确标注为故障演练。

部署可以在本机或云端使用已学方式，重点是从空数据库与明确依赖版本开始可复现。提供配置示例、初始化、启动、健康检查、测试、停止和清理说明；清理脚本不触及课程库及其他项目。

## 建议执行分配

| 工作 | 时间 |
|---|---:|
| 需求、角色、状态表与接口约定 | 10小时 |
| 数据库设计与核心CRUD | 20小时 |
| 登录、权限与输入校验 | 15小时 |
| 状态流转、事务与并发更新 | 20小时 |
| 关键测试、排错与回归 | 15小时 |
| 可复现部署与运行检查 | 10小时 |
| 查询优化证据与技术说明 | 10小时 |
| 合计 | 100小时 |

时间不足先移除可选扩展，保住业务正确性和关键测试。额外75小时补弱预算可以用于返修，但不要把全部问题拖到最后。

## 完成目标

交付自行编写并能维护的代码、数据库初始化与演示数据、接口说明、自动化测试、运行README、一次有依据的查询改进记录，以及项目设计与局限说明。能从一个请求追踪到权限、业务校验、事务、SQL和响应；能独立修改一条业务需求，并解释为什么这样设计。

基础阶段不使用AI代写。复杂项目可部分使用AI，但必须读懂关键执行路径、处理错误、修改需求并核对结果；不能解释的功能不作为已掌握能力展示。学习检查与技术追问训练计入预算，简历、投递、模拟和正式面试另计。

完成目标不作为记录用户完成事实的证明要求。用户明确说明完成、订正、掌握或实际用时时，直接按具体范围记录；后续代码检查与历史完成情况分别保存。
